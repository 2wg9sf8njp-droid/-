# 統合ライフコーチ 保守スキル

このアプリはユーザーが毎日スマホで使っている実運用中の家計簿・食事記録で、データは端末の IndexedDB にしか存在しない。サーバーもバックアップの自動同期も無い。つまり **変更で既存データが読めなくなると、ユーザーの数か月分の記録が失われる**。見た目のバグは直せば済むが、データ互換性の事故は取り返しがつかない。この非対称性が以下のすべてのルールの理由になっている。

## まず全体像をつかむ

`index.html`(約1500行)1ファイルに全部入っている。`<script>` の中は元々別ファイルだった名残で、コメントの見出しで4つの層に分かれている:

| 層 | 見出し | 役割 | 公開オブジェクト |
|---|---|---|---|
| 定数 | `// data.js` | 費目 `MAIN_CATEGORIES`、収入ラベル、予定タイプ | `window.APP_DATA` |
| 永続化 | `// db.js` | IndexedDB、`KV_DEFAULTS`、エクスポート/インポート | `window.DB` |
| AI | `// ai.js` | Anthropic API をブラウザから直接呼ぶ、プロンプト | `window.AI` |
| 画面 | `// app.js` | ユーティリティ、タブ描画、`init()` | — |

作業前に `grep -n -E '^// [a-z]+\.js|^(async )?function |^let ' index.html` で現在の関数と状態変数の位置を確認するとよい(行番号は変わるので覚えずに毎回調べる)。

**画面の仕組み**: 下部ナビの `button[data-tab=X]` → `switchTab(X)` → `RENDERERS[X](section#view-X)`。各 `renderXxx(container)` が `container.innerHTML` をテンプレート文字列で丸ごと作り直し、その後 `querySelector(...).onclick = ...` でイベントを付ける。タブ内のサブ画面は `.seg` ボタン + モジュールスコープの `let xxxView` で切り替え、変更後は親の render 関数を呼び直す。フレームワークは使っていない。

**データの置き場所**:
- `kv` ストア: 設定や単一の値(goals, profile, apiKey, fixedCosts, categoryBudgets, schedule, planCandidates, committedWeek, pastCommits, feedbackLog…)。`DB.kvGet/kvSet` で読み書き。
- `expenses` / `incomes` / `meals` ストア: 明細。`dateISO`("YYYY-MM-DD")と `monthKey`("YYYY-MM")、`createdAt` を持つ。

## 守ること(理由つき)

### データ互換性 — 最重要
- **`DB_NAME`("lifecoach_db")を変えない。** 変えると別DBが作られ、既存データが見えなくなる。
- **スキーマは加算のみ。** ストアやインデックスを追加するときは `DB_VERSION` を1上げ、`onupgradeneeded` に「`contains` で無ければ作る」を足す。既存ストアの削除・リネーム・`deleteIndex` はしない。古いバージョンのデータのままでもアプリが開けることが前提。
- **既存レコードのフィールド名・意味を変えない。** 新しいフィールドを足すのはよいが、古いレコードにはそれが無いので、読む側で `r.newField ?? 既定値` のように欠けている場合を必ず扱う。
- **新しい kv キーは必ず `KV_DEFAULTS` に足す。** `exportAllData` は `KV_DEFAULTS` のキーだけをバックアップするので、足し忘れるとバックアップから黙って漏れる。既定値も既存ユーザーの初回読み込み時に使われる。
- **バックアップ形式 `"life-coach-mobile.v1"`**: フィールド追加だけなら v1 のままでよい(インポート側で欠けを許容する)。形を変える必要があるなら v2 を作り、`importAllData` は v1 も引き続き読めるようにする。ユーザーの手元の古いバックアップファイルが唯一の保険だから。
- **費目名 `MAIN_CATEGORIES` のリネームに注意。** 過去の支出・予算・固定費は文字列で費目を保存している。名前を変えると過去データが「どの費目にも属さない」状態になる。リネームを頼まれたら、過去データの扱い(移行処理を書く/旧名も残す)をユーザーに確認する。追加と並べ替えは安全。

### 単一ファイル・オフライン
- **外部の JS/CSS/フォント/画像を読み込まない。** スマホのホーム画面から開くローカルファイルとして使われるので、CDN は圏外やファイル直開きで動かない。アイコンは data URI、図はインラインSVG、ライブラリが要るなら自前で小さく書く。
- 通信してよいのは `ai.js` の `https://api.anthropic.com/v1/messages` だけ。APIキーは端末内にのみ保存し、他所へ送らない(設定画面でユーザーにそう約束している)。
- service worker は使っていない(単一ファイル版のため)。

### コードの書き方
- 既存の流儀に合わせる: 素の JS、テンプレート文字列 + `el()`/`innerHTML`、`async/await`、日本語コメント。クラスやビルドツールを持ち込まない。
- **ユーザー入力や保存データを HTML に埋め込むときは必ず `escapeHTML()` を通す。** メモ欄や AI の応答がそのまま innerHTML に入るため。
- 金額表示は `yen()`、日付は `DB.todayISO()` / `isoDate()` / `formatDateLabel()` を使う。`new Date().toISOString()` を直接使うと UTC になり、日本時間の朝9時前に日付がずれる。
- 通知は `toast("…")`、画面内のエラー表示は `<p class="issue">`、成功は `<p class="ok-line">`。
- 新しいタブを足すなら、ナビボタン・`section#view-X`・`RENDERERS` の3点セットを揃える(ナビは5つで既に横幅いっぱいなので、まずは既存タブ内の `.seg` サブ画面で済まないか検討する)。

### 見た目
- 色は `:root` の CSS 変数(`--green`, `--paper`, `--ink`, `--muted`, `--red`, `--gold` など)だけを使い、新しい色が要るなら変数として足す。
- 既存の部品を再利用する: `.card` `.card-title` `.btn` (`.btn-green`/`.btn-outline`/`.btn-red`/`.btn-sm`) `.seg` `.chip` `.row` `.progress-*` `.muted` `.tag-*` など。
- 幅は最大460px のスマホ前提。タップしやすさ(ボタン高さ 40px 前後)と、片手で届く下側配置を意識する。
- 文言はです・ます調の日本語。専門用語は避け、AI の提案には「断定しない」トーンを保つ。

### AI まわり
- モデルは `AI_MODEL` 定数1か所で管理している。変えるときはここだけ。
- AI には「JSON のみで返す」よう頼み、`callClaudeJSON` でパースしている。出力形式を変えるときは、プロンプトの出力形式例と、それを読む画面側のコードを両方直す。
- 費目名はプロンプトに `categoryListText()` で埋め込んでいるので、費目を足せば AI 側にも自動で反映される。
- エラーは `AIError` で投げ、日本語のわかりやすいメッセージにする。

## 作業の流れ

1. **依頼を読み解く。** 曖昧なら、何をどの画面で実現したいかを確認する。データ形式に影響する変更(費目のリネーム、フィールドの意味変更など)は、着手前に影響を説明して合意をとる。
2. **該当箇所を grep で特定して読む。** 似た既存機能があればそれを手本にする。
3. **最小限の変更を入れる。** 頼まれていないリファクタや整形はしない(差分が読みにくくなり、ユーザーが確認しにくくなる)。
4. **チェックを走らせる**(リポジトリのルートで):
   ```bash
   node .claude/skills/lifecoach-maintain/scripts/check.mjs index.html
   node .claude/skills/lifecoach-maintain/scripts/smoke.mjs index.html <スクショ保存先>
   ```
   - `check.mjs`: JS 構文、外部リソース依存、DB_NAME/削除系API、`KV_DEFAULTS` の登録漏れ、タブの3点セット、未定義の CSS 変数などを静的に検査する。
   - `smoke.mjs`: スマホ幅のヘッドレスブラウザで全タブと `.seg` サブ画面を巡回し、JS エラーが無いか、バックアップの往復でデータが変わらないかを見る。Playwright が無ければ自動でスキップする。
   - 変更した画面は、保存したスクリーンショットを実際に見て崩れていないか確かめる。新機能の操作(保存→再表示など)は、必要に応じて Playwright で個別に試す。
5. **報告する。** 何を変えたか、データ互換性への影響(「既存データにはそのまま使えます」/「〜の移行が必要」)、確認した内容をユーザーにわかる言葉で伝える。コミットを頼まれたら、変更内容がわかる日本語のメッセージでコミットする。

## よくある依頼の手順メモ

- **費目を追加**: `MAIN_CATEGORIES` に追加するだけ。予算・月次・AI プロンプトには自動で反映される。「貯金」は特別扱い(変動費から除外)なので、似た性質の費目なら `"貯金"` を参照している箇所を grep して扱いを揃える。
- **設定項目を追加**: `KV_DEFAULTS` に既定値を足す → `renderSettings` にカードを足す → 使う側で `DB.kvGet`。
- **明細に項目を追加**(例: 支出に支払方法): `addExpense` の引数とレコードに足す → 入力UI → 表示側は欠けている古いレコードを考慮。インデックスで検索したい場合だけ `DB_VERSION` を上げて `createIndex` を加算する。
- **過去日付での記録**: 現状 `addExpense` などは常に `todayISO()` を使う。対応するなら `dateISO` を任意引数にして、`monthKey` も必ずそこから計算する。
